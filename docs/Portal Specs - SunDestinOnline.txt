Before deleting `C:\Downloads\npp.8.5.3.portable.x64`, back up the important Notepad++ settings, unsaved documents, sessions, and customizations.

For a portable Notepad++ installation, most settings are stored inside the application folder itself.

## 1. Important files to back up

| File / Folder        | Contents                                         | Priority            |
| -------------------- | ------------------------------------------------ | ------------------- |
| `backup\`            | Automatic backups of unsaved or edited documents | Critical            |
| `session.xml`        | Previously opened tabs and file locations        | High                |
| `config.xml`         | General preferences and settings                 | High                |
| `shortcuts.xml`      | Custom keyboard shortcuts and macros             | High                |
| `userDefineLang.xml` | Custom language definitions                      | High                |
| `userDefineLangs\`   | Additional user-defined language files           | High, if present    |
| `functionList\`      | Customized function parsing definitions          | Medium              |
| `plugins\config\`    | Plugin configuration and settings                | High, if customized |
| `stylers.xml`        | Syntax highlighting and style settings           | Medium              |
| `themes\`            | Custom themes, if any                            | Medium              |
| `contextMenu.xml`    | Customized right-click menus                     | Medium              |
| `nativeLang.xml`     | Language interface configuration                 | Low                 |
| `langs.xml`          | Language syntax configuration, if customized     | Low                 |

Most important: Check the `backup\` folder before deleting anything. It may contain recoverable unsaved text from Notepad++ tabs.

## 2. Recommended backup method

Since the portable application is relatively small, the safest approach is to back up the entire folder before uninstalling.

1. Close Notepad++ completely so settings and session data are saved.
2. Go to `C:\Downloads\`.
3. Right-click `npp.8.5.3.portable.x64` and choose Compress to ZIP file (or Send to → Compressed folder).
4. Rename the ZIP to `NotepadPP_8.5.3_Backup.zip`.
5. Move the ZIP outside the folder you intend to delete, ideally to another drive or your backup location.

This preserves plugins, settings, recovery files, and any user documents stored within the portable folder.

## 3. Check these additional locations

If portable mode was overridden or cloud settings were enabled, some configuration files might be elsewhere:

- `%AppData%\Notepad++`
- An alternate settings directory specified using `-settingsDir`
- Any custom Notepad++ cloud settings folder

To verify, open Notepad++ → ? → Debug Info and look for `Local Conf mode: ON`.&#x20;

# MASTER ARCHITECTURE PROMPT

## Secure, Privacy-First Vacation Rental Booking Platform

### ROLE

Act as a senior software architect, application security architect, privacy engineer, and full-stack developer.

Design and implement a production-ready vacation rental booking website that prioritizes:

1. Very high security against common cyberattacks.
2. Strong guest and property-owner privacy.
3. Simple, widely supported web hosting.
4. Minimal infrastructure maintenance.
5. Low operating costs for an initial 1–5 properties.
6. Easy deployment, upgrades, backups, and recovery.
7. Portability and avoidance of unnecessary vendor lock-in.

No application can be guaranteed hack-proof. Use defense in depth, established frameworks, and secure-by-default configurations. Do not claim compliance or security certification without verification.

### 1. REQUIRED TECHNOLOGY STACK

Use the following baseline:

- Frontend: React + TypeScript + Vite.
- Styling: Simple responsive CSS or Tailwind CSS.
- Website hosting: Hostinger static hosting, compatible with standard static hosting providers.
- Version control: Private GitHub repository.
- DNS, CDN, edge security: Cloudflare.
- Database: Managed Supabase PostgreSQL.
- Authentication: Supabase Auth.
- Backend: Supabase Edge Functions and secure PostgreSQL functions.
- Payments: Stripe-hosted Checkout.
- File storage: Supabase Storage with private buckets where necessary.
- Email: Managed transactional email service.
- Monitoring: Managed error, uptime and security alerts.
- Backups: Automated backups plus periodic independently stored exports.

Prefer managed services over operating servers.

Do not introduce a VPS, Kubernetes, container orchestration, custom authentication infrastructure, self-hosted database, or microservices unless a demonstrated requirement makes them necessary.

Keep the frontend deployable to ordinary static hosting, without server-side rendering requirements.

### 2. BUSINESS FUNCTIONALITY

The platform must support:

- Public property listings with photos, descriptions, amenities and locations.
- Availability calendars.
- Nightly and seasonal pricing.
- Guest selection of check-in and check-out dates.
- Minimum-night and maximum-occupancy restrictions.
- Booking quotations including mandatory fees, taxes and optional charges.
- Secure guest contact information collection.
- Reservation holds and confirmation.
- Stripe-hosted payments.
- Guest booking confirmation emails.
- Owner/administrator reservation management.
- Owner calendar blocks.
- Booking cancellations and modifications.
- External calendar import/export using iCal.
- Multiple properties with independent calendars.
- Booking and payment audit trails.

Guests should be able to browse without creating an account. Use guest checkout unless an account is genuinely required.

### 3. APPLICATION SECURITY

Use OWASP ASVS 5.0 Level 2 as the verification baseline, with stronger controls for sensitive operations.

Implement:

- HTTPS everywhere, with appropriate HSTS and TLS configuration.
- Secure response headers including Content Security Policy, nosniff, and suitable referrer policy.
- Strict input validation, output encoding, and parameterized database queries.
- Protection against XSS, SQL injection, CSRF where applicable, IDOR/BOLA and common API vulnerabilities.
- Deny-by-default server-side access control.
- No unnecessary database tables directly exposed through public APIs.
- PostgreSQL Row Level Security on every exposed table.
- Privileged database actions isolated behind carefully reviewed server-side functions.
- No service-role keys, database passwords, payment secrets or private API credentials in client code.
- Secure environment variable and secret management.
- Rate limiting, bot mitigation, and anti-automation protections for sensitive functions.
- Secure CORS configuration with explicitly approved origins.
- Safe file-upload validation, file size limits and controlled download permissions.
- Non-verbose error responses that do not reveal internal architecture or secrets.
- Secure, current dependencies and automated vulnerability monitoring.

Never treat a frontend restriction as a security boundary.

Verify that all direct backend endpoints remain protected even if an attacker bypasses Cloudflare and calls the service provider's API hostname directly.

### 4. AUTHENTICATION AND AUTHORIZATION

Use Supabase Auth; do not implement custom password storage.

Define the following roles:

- Public visitor.
- Guest.
- Property owner.
- Administrator.

Require MFA for owners and administrators.

Use least-privilege authorization, with property-level isolation. An owner must only access assigned properties and reservations.

Prevent horizontal and vertical privilege escalation.

Implement secure session expiration, password recovery, account deactivation, login rate limiting and suspicious-login logging.

Do not expose administrative operations merely by hiding them from the user interface.

### 5. PRIVACY BY DESIGN

The application must collect only the information needed to operate the booking service.

Typical required information:

- Guest name.
- Contact email.
- Contact phone where operationally necessary.
- Reservation dates and property.
- Number of guests.
- Booking charges and payment reference.

Additional guest information must be justified by business or legal requirements.

Requirements:

- Do not store credit card numbers or CVV data.
- Do not collect unnecessary identity documents.
- Do not use advertising or behavioral tracking scripts by default.
- Use first-party, privacy-conscious analytics where possible.
- Publish a clear privacy policy and data retention schedule.
- Support authenticated requests for account/data deletion, subject to legal retention duties.
- Separate operational data from analytics data.
- Minimize personal information in logs.
- Do not place guest names or private reservation details in public calendar feeds.
- Use private object storage for confidential files.
- Restrict third-party providers to the minimum data needed for service delivery.
- Encrypt sensitive data in transit and at rest; apply additional application-level encryption only where justified, with managed keys and rotation procedures.
- Evaluate applicable privacy laws based on customer location and business operations.

Document what guest data is shared with hosting, payment, email, authentication and monitoring providers.

### 6. BOOKING AND PAYMENT INTEGRITY

The booking engine must be safe under simultaneous requests.

Requirements:

- Treat check-in as inclusive and check-out as exclusive.
- Enforce availability using atomic database operations.
- Prevent overlapping confirmed reservations and active holds.
- Never rely only on frontend calendar status.
- Use time-limited booking holds.
- Calculate final prices on the server.
- Never trust prices submitted by the browser.
- Use Stripe-hosted checkout sessions created securely by the backend.
- Verify Stripe webhook signatures using the exact raw request body.
- Use idempotency for booking and payment operations.
- Independently verify payment status, amount, currency, checkout session and matching booking before confirmation.
- Handle expired holds, delayed webhooks, repeated events and payment failures.
- Do not issue a confirmed reservation until payment and inventory conditions are satisfied.
- Maintain reconciliation procedures and alerts for exceptional payment/booking states.

External iCal imports are eventually consistent, not real-time. Clearly document double-booking risks and required operational procedures.

### 7. HOSTING AND NETWORK ARCHITECTURE

Design a deployment that works with common static hosting.

Frontend deployment:

1. Store source code in private GitHub.
2. Build the static frontend through a controlled CI/CD workflow.
3. Execute linting, tests, dependency audits and security checks.
4. Deploy only compiled static assets to Hostinger.
5. Attach the custom domain through Cloudflare DNS.
6. Enable HTTPS and suitable security response headers.
7. Protect deployment credentials and restrict production publishing.
8. Maintain rollback to a previously validated release.

Backend deployment:

1. Use a separate Supabase project for production.
2. Deploy schema through version-controlled migrations.
3. Deploy Edge Functions with environment-managed secrets.
4. Require authorization and appropriate rate controls for protected functions.
5. Separate development and production credentials.
6. Never expose privileged keys to browsers.

Document exact DNS, TLS, CORS, callback URLs and custom-domain configuration.

Do not assume that Cloudflare protecting the static website also protects Supabase API endpoints. Configure provider-native protections and independent API abuse controls.

### 8. DATABASE AND STORAGE

Define a minimal normalized schema including:

- properties
- property_owners
- users/profiles
- owner_property_assignments
- reservations
- reservation_holds
- calendar_blocks
- nightly_rates
- stay_rules
- payments
- calendar_sync_sources
- calendar_events
- audit_logs

Include:

- Primary keys, foreign keys and appropriate indexes.
- Constraints and transactional reservation conflict protection.
- Explicit read/write permissions by role.
- Row Level Security policies and tests.
- Separation between public property content and private guest records.
- Data retention and archival rules.
- Migration and rollback strategy.

Do not duplicate sensitive guest information across tables unnecessarily.

### 9. OPERATIONAL SECURITY

Implement a realistic operating model for a small website owner.

Required:

- MFA on hosting, GitHub, Cloudflare, Supabase, Stripe and email-provider administrator accounts.
- Minimal administrator access.
- Protected production branches and deployment approvals.
- Dependency vulnerability alerts.
- Secret scanning and secret rotation procedures.
- Monitoring of failed logins, suspicious API activity and payment anomalies.
- Security event retention without unnecessary PII.
- Automatic backups with verified recovery procedures.
- Periodic restoration testing in an isolated environment.
- Documented incident response and credential-compromise recovery.
- Defined recovery point and recovery time objectives.
- Regular software updates and security review.

Describe which controls are available on free plans and which require paid services. Do not assume enterprise features are included by default.

### 10. TESTING AND RELEASE GATES

Provide automated and manual tests for:

- Unauthenticated access to private reservation data.
- Cross-account and cross-property data access.
- Unauthorized owner/admin actions.
- SQL injection and XSS.
- CSRF where relevant.
- API abuse and rate-limit effectiveness.
- Booking race conditions.
- Overlapping holds and reservations.
- Price manipulation.
- Duplicate or forged payment webhooks.
- Expired checkout sessions.
- Malicious file uploads.
- Accidental secret exposure.
- Calendar synchronization conflicts.
- Recovery from backup.
- Failure of external providers.

Do not launch until all critical and high-risk findings have been resolved or appropriately mitigated and documented.

### 11. IMPLEMENTATION PRINCIPLES

Favor simplicity and proven libraries.

- Start with the smallest secure working implementation.
- Minimize third-party packages.
- Do not build abstractions without a concrete use case.
- Prefer configuration over complex customization.
- Use type-safe interfaces and clearly defined APIs.
- Maintain a straightforward project structure.
- Include explanatory comments only where they add value.
- Document all necessary secrets without printing their values.
- Avoid unsupported security claims.
- Identify every manual setup task explicitly.
- Never silently weaken security to make deployment easier.
- Make the architecture portable to another static hosting provider.

### 12. REQUIRED DELIVERABLES

Produce these outputs in order:

1. Architecture diagram and component responsibilities.
2. Threat model: critical assets, attackers, attack paths and mitigations.
3. Technology selection with rationale and lower-complexity alternatives.
4. Network and data-flow diagrams, including trust boundaries.
5. Database schema with RLS policy designs.
6. Authentication and authorization design.
7. Booking and Stripe transaction sequence.
8. Privacy and retention matrix.

### 13. EXECUTION INSTRUCTIONS

First produce the architecture and security design.

Then implement in small, verifiable stages:

Stage A: Static property website and secure deployment.

Stage B: Database, authentication and property administration.

Stage C: Availability calendar, reservation holds and price calculations.

For every stage, specify:

- Files or components created.

## 14. Authentication (ATN), Authorization (ATZ) and Zero Trust

Implement centralized identity using Supabase Auth.

### Authentication

- Support Google OAuth sign-in for personal Gmail and eligible Google Workspace accounts.
- Support Microsoft OAuth sign-in for eligible Outlook, Hotmail, Live and Microsoft organizational accounts.
- Support email one-time-password (OTP) login for any valid email address, including Yahoo and corporate email accounts.
- Implement a production transactional email/SMTP provider with SPF, DKIM and DMARC configured.
- Do not require guests to create separate application passwords.
- Offer optional account creation and guest checkout.
- Support enterprise SAML/OIDC identity providers as a future extension where commercially and technically supported.
- Validate identity-provider tokens, configured audiences, issuers, expiration and callback destinations using managed authentication libraries.
- Avoid requesting access to users' Gmail, Outlook, contacts, mailboxes, or files. Request only identity scopes needed for login.
- Rate-limit OTP requests and verification attempts; prevent account enumeration.
- Use secure session management and reauthentication for sensitive account changes.
- Enable MFA and recent reauthentication for privileged owner and administrator actions.

### Authorization

- Default every authenticated account to the Guest role.
- Never grant Owner/Admin privileges based solely on email address or email domain.
- Store trusted role assignments and property ownership mappings server-side.
- Use database Row Level Security for property-level and reservation-level isolation.
- Restrict guest access to their own verified reservations.
- Require server-side authorization for all administrative functions.
- Use explicit invitation and approval processes for owner access.
- Revoke owner and administrator permissions immediately when access is removed.

### Account and identity linking

- Maintain one canonical application user ID.
- Support multiple verified identities linked to that user when safe and supported.
- Prevent duplicate guest accounts where possible without weakening identity verification.
- Never merge accounts simply because a user enters an email address.
- Require strong verification for linking accounts that have privileged access.
- Treat enterprise SSO accounts separately where provider restrictions apply.
- Keep an audit trail of identity linking and privilege changes.

### Zero Trust

- Authenticate and authorize every protected API operation.
- Never trust a browser, email domain, device, IP address, or frontend role indicator by itself.
- Validate resource ownership on every protected request.
- Apply least-privilege access to database, storage and backend functions.
- Keep credentials and payment operations server-side.
- Use short-lived credentials where supported.
- Log privileged actions without exposing personal information or authentication secrets.
- Test access denial for every unauthorized role and resource combination.

### Acceptance criteria

- Gmail user can sign in using Google.
- Microsoft user can sign in using Microsoft.
- Yahoo or other email user can sign in using OTP.
- Corporate email user can sign in using OTP even without SSO.
- Guest cannot access another guest's reservation.
- Owner A cannot access Owner B's properties.
- A user cannot promote themselves to Administrator.
- Expired, invalid and replayed authentication credentials are rejected.
- MFA is required before privileged administration.
- Removing access prevents subsequent protected operations.

One additional security consideration: users may log in with multiple methods, but linking identities requires careful handling, especially for privileged accounts. Supabase documents automatic and manual identity linking, with specific restrictions for SAML SSO accounts.&#x20;

### 2.2 Calendar selection rules

The platform must distinguish between occupied nights and arrival/departure dates.

For example, a reservation checking in June 10 and checking out June 15 occupies five nights: June 10–14. June 15 becomes available for a new arrival unless an owner-defined turnover restriction applies.

The guest must not be allowed to submit an invalid booking, including a date range containing blocked nights or one that violates minimum-stay, advance-notice, or arrival restrictions.

### 4.2 Core business rules

- BR-01: Each property has a separate availability calendar.
- BR-02: Booking date ranges use check-in inclusive, check-out exclusive logic.
- BR-03: Two active bookings must never occupy the same property-night.
- BR-04: Pending payments may hold inventory for a configurable period, such as 10–15 minutes.
- BR-05: Expired holds automatically release availability, subject to payment reconciliation.
- BR-06: Cancellations release booked nights according to the applicable cancellation workflow.
- BR-07: Reservation date modifications must be checked atomically against current availability.
- BR-08: Calendar synchronization failures must produce an alert and retry workflow.
- BR-09: Server-side availability checks are authoritative; the visual calendar is informational.
- BR-10: Calendar dates use the property's configured local time zone.
- BR-11: Pricing and availability must be revalidated immediately before booking confirmation.
- BR-12: Late payment notifications must not confirm a reservation whose hold has expired or whose dates have been allocated elsewhere.

## 6. Pricing and date restrictions

The calendar should support a pricing hierarchy:

1. Property default nightly rate.
2. Seasonal rate adjustment.
3. Weekend or weekday pricing.
4. Holiday or special-event pricing.
5. Manual date-specific override.
6. Discounts for weekly, monthly, or promotional stays.

The system must use a documented precedence order so that every date resolves to one final nightly rate. Property-specific overrides should normally take priority over automated rates unless an administrator explicitly configures otherwise.

Additional calendar restrictions include advance booking windows, same-day bookings, minimum nights, maximum nights, check-in/check-out days, preparation buffers, and maximum occupancy.

Step-by-Step Georgia LLC Registration Guide

If you are planning to form your business yourself, I highly recommend using the online portal to minimize processing delays. Here are the concrete steps required to complete your registration:
• Step 1: Choose a Distinguishable Name: Your business name must be entirely unique from existing entities registered in Georgia. It must include an official designator like "Limited Liability Company," "LLC," or "L.L.C.". You can run a free availability check using the state's online business database. Optional 30-day name reservations are available for $25.

• Step 2: Appoint a Georgia Registered Agent: Georgia law requires you to name a registered agent who maintains a physical street address within the state (P.O. boxes are prohibited). They must be available during regular business hours to accept legal and official correspondence. You can act as your own agent if you have a physical presence in the state, or hire a commercial service to keep your home address off the public record.

• Step 3: File the Articles of Organization: Create a user account on the Georgia eCorp Portal and select "Create or Register a Business". You will input your principal office address, your registered agent details, and the LLC organizers.
	• Online Filing: $100 fee. Standard processing takes roughly 7 business days.
	• Mail or In-Person Filing: $110 fee ($100 fee + $10 paper service fee). Mail-in processing takes roughly 15 business days. You must submit Form CD 030 along with Transmittal Form 231.
	
• Step 4: Draft an Operating Agreement: This internal document dictates the LLC's financial management, member percentages, and structural rules. Georgia does not require you to file this with the Secretary of State, but business banks typically ask for one to open an account.

• Step 5: Obtain an EIN from the IRS: Once the state approves your LLC, visit the official IRS portal to acquire a free Employer Identification Number (EIN). This functions like a Social Security number for your entity and is vital for taxes and hiring personnel.
